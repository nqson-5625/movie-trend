--------------------------------------------------------------------------------
1. PHÂN TÍCH VÀ LỰA CHỌN GIẢI PHÁP KỸ THUẬT
--------------------------------------------------------------------------------

Để chuyển dữ liệu từ Kafka vào HDFS trong đồ án này, có 3 phương án:

1. Dùng Kafka Connect (HDFS 3 Sink Connector):
   - Đánh giá: Đây là chuẩn doanh nghiệp, nhưng Kafka Connect chạy trên JVM riêng 
     ngốn ít nhất 1.0 GB - 1.5 GB RAM. Trên máy ảo Ubuntu 8 GB đang chạy đồng thời 
     Kafka, HDFS, Spark, Elasticsearch, việc bật thêm Kafka Connect sẽ dẫn đến nguy cơ 
     bị Linux OOM Killer tiêu diệt tiến trình NameNode hoặc Elasticsearch.
   - Kết luận: Không khuyến nghị cho môi trường 8 GB RAM.

2. Dùng Spark Structured Streaming để ghi file xuống HDFS:
   - Đánh giá: Spark Streaming trong đề tài đã được giao cho Module 05 (Thắng + Hiếu) 
     chịu trách nhiệm cho Speed Layer (đẩy vào Elasticsearch). Nếu bắt Spark ghi micro-batch 
     xuống HDFS sẽ tạo ra hàng nghìn file rất nhỏ (Small File Problem), làm kiệt quệ 
     bộ nhớ của NameNode.
   - Kết luận: Không phù hợp.

3. Dùng Python Ingestion Daemon (GIẢI PHÁP TỐI ƯU NHẤT):
   - Đánh giá: 
     + Tiêu tốn cực kỳ ít RAM: chỉ khoảng 30 MB - 60 MB RAM.
     + Kiểm soát 100% logic: bóc tách `event_time` để phân vùng `dt=YYYY-MM-DD`.
     + Xử lý linh hoạt gom lô (Micro-batching theo 200 records hoặc 30 giây) 
       để tránh tạo file rác nhỏ trên HDFS.
     + Bắt lỗi và cách ly bản ghi hỏng vào `/quarantine/` theo đúng DATA_CONTRACT.md.
     + Cam kết At-least-once: chỉ commit offset khi ghi file HDFS thành công.
   - Kết luận: KHUYẾN NGHỊ SỬ DỤNG.

--------------------------------------------------------------------------------
2. NGUYÊN LÝ HOẠT ĐỘNG CỦA PYTHON SINK DAEMON
--------------------------------------------------------------------------------

1. Consumer kết nối tới Kafka Broker (mặc định: `127.0.0.1:9092` hoặc `kafka-svc.bigdata:9092`).
2. Subscribe 2 topics: `movie-events` và `tmdb-snapshots`.
3. Nhận từng message:
   - Parse JSON.
   - Kiểm tra tính hợp lệ của schema (JSON Schema Draft 2020-12, required fields, SHA-256 event_id).
   - Nếu hợp lệ:
     * Trích xuất ngày từ `event_time` (UTC) -> `dt=YYYY-MM-DD`.
     * Đưa vào Raw Buffer theo từng partition ngày.
   - Nếu không hợp lệ (JSON hỏng hoặc vi phạm schema):
     * Đưa vào Quarantine Buffer kèm lý do lỗi: `error_reason` và `error_time`.
4. Cơ chế Flush Buffer xuống HDFS:
   - Flush khi Buffer đạt 200 records HOẶC sau mỗi 30 giây không có message mới.
   - Tên file sinh ra: `part-<timestamp>-<count>.jsonl` (cho Raw) hoặc `error-<timestamp>-<count>.jsonl` (cho Quarantine).
   - Ghi file qua WebHDFS REST API hoặc `kubectl exec` trực tiếp vào Pod NameNode.
   - Commit offset đồng bộ sau khi file HDFS đóng an toàn.

--------------------------------------------------------------------------------
3. VẬN HÀNH VÀ KIỂM THỬ TỰ ĐỘNG
--------------------------------------------------------------------------------

1. Khởi chạy Daemon:
   make -C modules/hdfs sink
   (hoặc: python modules/hdfs/scripts/kafka_hdfs_sink.py)

2. Chạy bộ kiểm thử tự động luồng Sink:
   make -C modules/hdfs test-sink
   (hoặc: python modules/hdfs/tests/test_kafka_hdfs_sink.py)
   Kết quả: 8/8 tests PASS 100%.

3. Chạy toàn bộ tests của Module HDFS:
   make -C modules/hdfs test
   (Bao gồm: test_flow_module_1_to_3.py và test_kafka_hdfs_sink.py -> 16/16 PASS).
